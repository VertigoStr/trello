## User Scenarios & Testing

### User Story 1 - Регистрация нового пользователя (Priority: P1)

Пользователь может создать новый аккаунт, указав имя, email и пароль.

**Why this priority**: Это базовая функция для доступа к системе. Без регистрации пользователи не могут начать работу с приложением. Это первый шаг в пользовательском пути.

**Independent Test**: Пользователь может открыть страницу регистрации, заполнить форму и создать аккаунт, после чего перенаправляется на главную страницу.

**Acceptance Scenarios**:

1. **Given** пользователь находится на странице регистрации, **When** пользователь вводит корректные имя, email и пароль, **Then** аккаунт создаётся и пользователь перенаправляется на главную страницу
2. **Given** пользователь вводит email, который уже зарегистрирован, **When** пытается создать аккаунт, **Then** система показывает ошибку "Email уже используется"
3. **Given** пользователь вводит пароль короче 8 символов, **When** пытается создать аккаунт, **Then** система показывает ошибку "Пароль должен содержать минимум 8 символов"
4. **Given** пользователь вводит некорректный email, **When** пытается создать аккаунт, **Then** система показывает ошибку "Некорректный формат email"
5. **Given** пользователь не заполнил обязательное поле, **When** пытается создать аккаунт, **Then** система подсвечивает поле и показывает ошибку валидации

---

### User Story 2 - Вход в систему (Priority: P1)

Зарегистрированный пользователь может войти в систему, используя email и пароль.

**Why this priority**: После регистрации пользователи должны иметь возможность войти в систему. Это основная функция для доступа к личным данным и доскам.

**Independent Test**: Пользователь может открыть страницу входа, ввести credentials и успешно аутентифицироваться.

**Acceptance Scenarios**:

1. **Given** пользователь имеет зарегистрированный аккаунт, **When** вводит корректные email и пароль, **Then** происходит вход и перенаправление на главную страницу
2. **Given** пользователь вводит неправильный пароль, **When** пытается войти, **Then** система показывает ошибку "Неверный email или пароль"
3. **Given** пользователь вводит email несуществующего аккаунта, **When** пытается войти, **Then** система показывает ошибку "Неверный email или пароль"
4. **Given** пользователь успешно вошёл, **When** переходит на другие страницы приложения, **Then** остаётся аутентифицированным
5. **Given** пользователь заблокирован после множественных неудачных попыток входа, **When** пытается войти, **Then** система показывает сообщение о блокировке

---

### User Story 3 - Выход из системы (Priority: P2)

Аутентифицированный пользователь может выйти из системы.

**Why this priority**: Важная функция безопасности, позволяющая пользователям завершить сеанс. Особенно важно на общих устройствах.

**Independent Test**: Пользователь может нажать кнопку выхода и вернуться на страницу входа.

**Acceptance Scenarios**:

1. **Given** пользователь аутентифицирован, **When** нажимает кнопку "Выйти", **Then** происходит разлогинивание и перенаправление на страницу входа
2. **Given** пользователь вышел, **When** пытается перейти на защищённую страницу, **Then** перенаправляется на страницу входа
3. **Given** пользователь вышел, **When** снова пытается войти, **Then** может успешно аутентифицироваться

---

### User Story 4 - Просмотр профиля пользователя (Priority: P2)

Аутентифицированный пользователь может просматривать и редактировать свой профиль.

**Why this priority**: Пользователи должны иметь возможность управлять своей учётной записью и видеть информацию о себе.

**Independent Test**: Пользователь может открыть страницу профиля и увидеть свои данные.

**Acceptance Scenarios**:

1. **Given** пользователь аутентифицирован, **When** переходит на /profile, **Then** видит своё имя и email
2. **Given** пользователь на странице профиля, **When** редактирует имя, **Then** изменения сохраняются
3. **Given** пользователь не аутентифицирован, **When** пытается перейти на /profile, **Then** перенаправляется на /login

---

### User Story 5 - Просмотр списка досок (Priority: P2)

Аутентифицированный пользователь видит список своих досок на главной странице.

**Why this priority**: Главная страница должна показывать пользователю его доски для быстрого доступа.

**Independent Test**: Пользователь видит список досок после входа в систему.

**Acceptance Scenarios**:

1. **Given** пользователь аутентифицирован, **When** переходит на /, **Then** видит список своих досок
2. **Given** у пользователя нет досок, **When** переходит на /, **Then** видит сообщение "У вас пока нет досок"
3. **Given** пользователь не аутентифицирован, **When** пытается перейти на /, **Then** перенаправляется на /login

---

### User Story 6 - Восстановление доступа (Priority: P3)

Пользователь может восстановить доступ к аккаунту через сброс пароля.

**Why this priority**: Пользователи забывают пароли. Эта функция снижает нагрузку на поддержку и улучшает пользовательский опыт.

**Independent Test**: Пользователь может запросить сброс пароля и получить инструкцию на email.

**Acceptance Scenarios**:

1. **Given** пользователь забыл пароль, **When** вводит email на странице восстановления, **Then** получает инструкцию по сбросу пароля на email
2. **Given** пользователь получил ссылку для сброса, **When** переходит по ссылке, **Then** может установить новый пароль
3. **Given** пользователь установил новый пароль, **When** пытается войти, **Then** может войти с новым паролем

---

### Edge Cases

- Что происходит, когда пользователь пытается зарегистрироваться с email, который уже используется?
- Как система обрабатывает вход с некорректным форматом email?
- Что происходит при попытке входа во время блокировки аккаунта (после множественных неудачных попыток)?
- Как система обрабатывает истёкшую ссылку для сброса пароля?
- Что происходит при потере соединения во время регистрации/входа?
- Как обрабатывается ситуация, когда токен аутентификации истёк во время работы?

## Requirements

### Functional Requirements

- **FR-001**: Система ДОЛЖНА предоставлять форму регистрации с полями: имя, email, пароль
- **FR-002**: Система ДОЛЖНА валидировать email на корректность формата (содержит @ и домен)
- **FR-003**: Система ДОЛЖНА валидировать пароль (минимум 8 символов)
- **FR-004**: Система ДОЛЖНА показывать ошибки валидации для каждого поля формы
- **FR-005**: Система ДОЛЖНА показывать ошибку "Email уже используется" при регистрации существующего email
- **FR-006**: Система ДОЛЖНА предоставлять форму входа с полями: email, пароль
- **FR-007**: Система ДОЛЖНА показывать ошибку "Неверный email или пароль" при неудачном входе
- **FR-008**: Система ДОЛЖНА перенаправлять на главную страницу после успешного входа/регистрации
- **FR-009**: Система ДОЛЖНА предоставлять кнопку/ссылку для выхода из аккаунта
- **FR-010**: Система ДОЛЖНА перенаправлять на страницу входа при попытке доступа к защищённой странице без аутентификации
- **FR-011**: Система ДОЛЖНА сохранять состояние аутентификации между перезагрузками страницы
- **FR-012**: Система ДОЛЖНА предоставлять страницу восстановления пароля с полем email
- **FR-013**: Система ДОЛЖНА отправлять email с инструкцией по сбросу пароля
- **FR-014**: Система ДОЛЖНА предоставлять страницу установки нового пароля по ссылке из email
- **FR-015**: Система ДОЛЖНА показывать сообщение об успешной смене пароля
- **FR-016**: Система ДОЛЖНА предоставлять страницу профиля с возможностью редактирования имени
- **FR-017**: Система ДОЛЖНА предоставлять главную страницу со списком досок пользователя
- **FR-018**: Система ДОЛЖНА показывать сообщение "У вас пока нет досок" если у пользователя нет досок

### Key Entities

- **User (Пользователь)**: Зарегистрированный пользователь системы. Имеет имя, email (уникальный), пароль (хешированный), статус активности, дату регистрации.
- **Session (Сессия)**: Аутентифицированный сеанс пользователя. Содержит токен доступа, время истечения, идентификатор пользователя.
- **PasswordResetToken (Токен сброса пароля)**: Временный токен для восстановления доступа. Имеет срок действия, привязку к пользователю, статус использования.

## Success Criteria

### Measurable Outcomes

- **SC-001**: Пользователь может завершить регистрацию менее чем за 1 минуту
- **SC-002**: Пользователь может войти в систему менее чем за 30 секунд
- **SC-003**: 95% пользователей успешно завершают регистрацию с первой попытки
- **SC-004**: 90% пользователей успешно входят в систему с первой попытки
- **SC-005**: Время отклика на действия аутентификации (вход/выход/регистрация) не превышает 2 секунд
- **SC-006**: Форма регистрации и входа корректно отображается на экранах от 320px до 1920px шириной

## Assumptions

- Backend API для регистрации и аутентификации уже реализован (002-auth-api feature)
- API предоставляет endpoints: POST /api/auth/register, POST /api/auth/login, POST /api/auth/logout, POST /api/auth/forgot-password, POST /api/auth/reset-password, GET /api/auth/me
- API возвращает JWT токен при успешной аутентификации
- Токен хранится в localStorage для сохранения сессии между перезагрузками браузера
- Приложение использует React + TypeScript + Vite для реализации
- Bootstrap 5 используется для стилизации и компонентов UI
- Страницы: /login, /register, /forgot-password, /reset-password, /profile, /dashboard, / (главная)
- Пользователи имеют стабильное интернет-соединение для работы с веб-приложением
- Email-рассылка настроена на стороне backend для восстановления пароля
- Мобильная версия интерфейса адаптируется автоматически (responsive design)
- Язык интерфейса — русский (по умолчанию для проекта)
