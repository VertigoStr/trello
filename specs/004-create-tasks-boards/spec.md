# Feature Specification: Создание задач и привязка к доскам

**Feature Branch**: `004-create-tasks-boards`
**Created**: 2026-03-25
**Status**: Draft
**Input**: User description: "создание задач и привязка их к доскам"

## Clarifications

### Session 2026-03-25

- Q: Какие роли пользователей могут работать с задачами и какие операции им доступны? → A: Расширенная модель: назначенный исполнитель задачи может редактировать задачу независимо от роли на доске
- Q: Как пользователи могут назначать и изменять исполнителя задачи? → A: Создатель задачи выбирает исполнителя из участников доски при создании; исполнитель может быть изменён пользователем с правами write на доску; сам исполнитель может снять с себя задачу
- Q: Как определяется позиция новой задачи и как работает перемещение задач? → A: Новая задача автоматически добавляется в конец колонки; перемещение между колонками — пользователь явно указывает целевую колонку и позицию (или перетаскивает); порядок в колонке управляется явно через drag-and-drop или кнопки
- Q: Как система должна обрабатывать ситуацию, когда два пользователя одновременно редактируют одну задачу? → A: Optimistic locking: при конфликте система отклоняет второе сохранение и показывает пользователю актуальные данные для повторного редактирования
- Q: Какие дополнительные атрибуты и статусы должны быть у задачи помимо базовых? → A: Базовый набор: название, описание, исполнитель, позиция, даты создания/обновления, soft delete. Статус задачи определяется колонкой, в которой она находится

## User Scenarios & Testing

### User Story 1 - Создание задачи в колонке доски (Priority: P1)

Пользователь может создать новую задачу в выбранной колонке доски, указав название, описание и исполнителя.

**Why this priority**: Это базовая функция системы управления задачами. Без возможности создания задач доска не имеет практической ценности. Это MVP функциональности.

**Independent Test**: Пользователь может создать задачу с названием в существующей колонке и увидеть её в списке задач колонки.

**Acceptance Scenarios**:

1. **Given** пользователь имеет доску с минимум одной колонкой, **When** пользователь вводит название задачи и нажимает "Создать", **Then** задача появляется в выбранной колонке
2. **Given** пользователь вводит название задачи (1-255 символов), **When** задача создаётся, **Then** задача сохраняется с указанным названием
3. **Given** пользователь вводит описание задачи (опционально), **When** задача создаётся, **Then** описание сохраняется вместе с задачей
4. **Given** пользователь не ввёл название задачи, **When** пытается создать задачу, **Then** система показывает ошибку валидации
5. **Given** пользователь создаёт задачу, **When** задача создаётся, **Then** создатель задачи становится её исполнителем по умолчанию
6. **Given** пользователь выбирает исполнителя из участников доски, **When** задача создаётся, **Then** выбранный пользователь назначается исполнителем
7. **Given** в колонке уже есть задачи, **When** создаётся новая задача, **Then** она добавляется в конец колонки

---

### User Story 2 - Просмотр задач в колонках доски (Priority: P1)

Пользователь может видеть все задачи в колонках доски с их текущим состоянием.

**Why this priority**: Просмотр задач — основная функция для работы с доской. Пользователь должен видеть задачи сразу после создания для подтверждения успешности операции.

**Independent Test**: Пользователь открывает доску и видит все задачи, сгруппированные по колонкам с правильным порядком.

**Acceptance Scenarios**:

1. **Given** в доске есть задачи в нескольких колонках, **When** пользователь открывает доску, **Then** задачи отображаются в соответствующих колонках
2. **Given** задачи имеют позицию в колонке, **When** отображаются задачи, **Then** они сортируются согласно позиции
3. **Given** задача имеет описание, **When** пользователь просматривает задачу, **Then** описание отображается вместе с названием

---

### User Story 3 - Редактирование задачи (Priority: P2)

Пользователь может изменить название и описание существующей задачи. Назначенный исполнитель может редактировать задачу независимо от своей роли на доске.

**Why this priority**: Позволяет корректировать задачи в процессе работы. Важно для практического использования, но не блокирует базовое создание задач.

**Independent Test**: Пользователь может изменить название существующей задачи и увидеть изменения.

**Acceptance Scenarios**:

1. **Given** задача существует, **When** пользователь редактирует название, **Then** изменения сохраняются
2. **Given** задача имеет описание, **When** пользователь обновляет описание, **Then** новое описание сохраняется
3. **Given** пользователь пытается установить пустое название, **When** сохраняет изменения, **Then** система показывает ошибку валидации
4. **Given** пользователь является исполнителем задачи, **When** редактирует задачу, **Then** изменения сохраняются независимо от роли на доске
5. **Given** пользователь не является исполнителем и не имеет прав write на доске, **When** пытается редактировать задачу, **Then** система отклоняет операцию

---

### User Story 4 - Перемещение задачи между колонками (Priority: P2)

Пользователь может перемещать задачи между колонками доски для изменения их статуса.

**Why this priority**: Ключевая функция Kanban-досок — перемещение задач по workflow. Важно для управления рабочим процессом.

**Independent Test**: Пользователь может переместить задачу из одной колонки в другую.

**Acceptance Scenarios**:

1. **Given** задача находится в колонке "To Do", **When** пользователь перемещает задачу в колонку "In Progress", **Then** задача отображается в новой колонке
2. **Given** задача перемещается между колонками, **When** операция завершается, **Then** позиция задачи в новой колонке устанавливается корректно
3. **Given** пользователь не имеет прав на редактирование доски, **When** пытается переместить задачу, **Then** система отклоняет операцию
4. **Given** пользователь перемещает задачу, **When** операция выполняется, **Then** задача добавляется в конец целевой колонки по умолчанию
5. **Given** пользователь использует drag-and-drop, **When** перетаскивает задачу, **Then** задача перемещается в указанную позицию

---

### User Story 5 - Удаление задачи (Priority: P3)

Пользователь может удалить задачу из колонки доски.

**Why this priority**: Важная функция управления, но не критична для базового рабочего процесса. Может быть реализована после основных CRUD операций.

**Independent Test**: Пользователь может удалить задачу, и она исчезает из колонки.

**Acceptance Scenarios**:

1. **Given** задача существует в колонке, **When** пользователь удаляет задачу, **Then** задача больше не отображается в колонке
2. **Given** задача была удалена, **When** пользователь обновляет доску, **Then** задача остаётся удалённой
3. **Given** пользователь не имеет прав на удаление, **When** пытается удалить задачу, **Then** система отклоняет операцию

---

### Edge Cases

- Что происходит, когда пользователь пытается создать задачу в несуществующей колонке? — Система возвращает ошибку
- Как система обрабатывает создание задачи с названием длиной более 255 символов? — Система возвращает ошибку валидации
- Что происходит при попытке переместить задачу в несуществующую колонку? — Система возвращает ошибку
- Как система обрабатывает одновременное редактирование одной задачи несколькими пользователями? — Optimistic locking: второе сохранение отклоняется, пользователю показываются актуальные данные
- Что происходит при удалении колонки, содержащей задачи? — Задачи удаляются каскадно
- Как система обрабатывает потерю соединения при создании/редактировании задачи? — Операция отменяется, данные не сохраняются

## Requirements

### Functional Requirements

- **FR-001**: Система ДОЛЖНА позволять пользователям создавать задачи с названием (1-255 символов) в выбранной колонке доски
- **FR-002**: Система ДОЛЖНА позволять добавлять опциональное описание к задаче (до 10000 символов)
- **FR-003**: Система ДОЛЖНА отображать все задачи доски, сгруппированные по колонкам
- **FR-004**: Система ДОЛЖНА сохранять порядок задач в колонке согласно позиции
- **FR-005**: Система ДОЛЖНА позволять пользователям редактировать название и описание существующих задач
- **FR-006**: Система ДОЛЖНА позволять перемещать задачи между колонками доски
- **FR-007**: Система ДОЛЖНА позволять удалять задачи из колонок доски
- **FR-008**: Система ДОЛЖНА проверять права доступа перед созданием, редактированием, перемещением и удалением задач. Назначенный исполнитель (assignee) может редактировать задачу независимо от своей роли на доске
- **FR-009**: Система ДОЛЖНА возвращать ошибку при попытке создать задачу с пустым названием
- **FR-010**: Система ДОЛЖНА возвращать ошибку при попытке создать задачу в несуществующей колонке
- **FR-011**: Система ДОЛЖНА возвращать ошибку при попытке работать с несуществующей задачей
- **FR-012**: Система ДОЛЖНА обновлять временную метку обновления задачи при редактировании
- **FR-013**: Система ДОЛЖНА каскадно удалять задачи при удалении колонки
- **FR-014**: Система ДОЛЖНА позволять создателю задачи назначать исполнителя из участников доски при создании
- **FR-015**: Система ДОЛЖНА позволять изменять исполнителя задачи пользователю с правами write на доске
- **FR-016**: Система ДОЛЖНА позволять исполнителю снять с себя задачу
- **FR-017**: Система ДОЛЖНА автоматически добавлять новую задачу в конец колонки
- **FR-018**: Система ДОЛЖНА позволять перемещать задачу в указанную позицию в целевой колонке (drag-and-drop или явное указание)
- **FR-019**: Система ДОЛЖНА использовать optimistic locking для предотвращения конфликтов при одновременном редактировании задачи

### Key Entities

- **Task (Задача)**: Основная единица работы на доске. Имеет название, описание, позицию в колонке, исполнителя (assignee), статус удаления (soft delete), даты создания и обновления. Принадлежит колонке. Исполнитель может редактировать задачу независимо от своей роли на доске. Статус задачи определяется колонкой, в которой она находится.
- **Column (Колонка)**: Контейнер для задач на доске. Содержит множество задач, упорядоченных по позиции. Принадлежит доске.
- **Board (Доска)**: Рабочее пространство, содержащее колонки с задачами. Имеет владельца и участников с правами доступа.
- **BoardMember (Участник доски)**: Связь пользователя с доской, определяющая роль и права доступа (read/write/delete).

## Success Criteria

### Measurable Outcomes

- **SC-001**: Пользователь может создать задачу с названием и описанием менее чем за 2 секунды
- **SC-002**: Список задач в доске загружается менее чем за 1 секунду для доски с до 100 задачами
- **SC-003**: 95% операций создания/редактирования задач завершаются успешно с первого раза
- **SC-004**: Пользователь может переместить задачу между колонками менее чем за 1 секунду
- **SC-005**: Система поддерживает одновременную работу с доской до 10 пользователей без конфликтов данных
- **SC-006**: 90% пользователей успешно создают первую задачу без обращения к документации

## Assumptions

- Пользователь уже аутентифицирован в системе перед работой с задачами
- Доска и колонки уже созданы перед добавлением задач
- Система использует существующую модель данных из 003-task-boards-crud (Board, Column, Task, BoardMember)
- Права доступа проверяются через существующий permission service из 003-task-boards-crud
- Мягкое удаление (soft delete) для задач уже реализовано в модели данных
- Пользователи имеют стабильное интернет-соединение для работы с веб-интерфейсом
- Мобильная версия интерфейса не входит в scope данной функции (веб-интерфейс адаптивен)
- Интеграция с существующим API аутентификации (002-auth-api) уже настроена
