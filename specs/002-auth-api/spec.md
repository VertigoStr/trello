## User Scenarios & Testing *(mandatory)*

### User Story 1 - Регистрация нового пользователя (Priority: P1)

Пользователь хочет создать новый аккаунт для доступа к системе управления задачами.

**Why this priority**: Это первая точка входа в систему — без регистрации пользователь не может получить доступ к основным функциям приложения.

**Independent Test**: Пользователь может создать аккаунт с уникальным email и получить доступ к системе.

**Acceptance Scenarios**:

1. **Given** пользователь не имеет аккаунта, **When** он вводит email, пароль и имя, **Then** создаётся новый аккаунт и пользователь получает токен доступа
2. **Given** пользователь вводит существующий email, **When** он пытается зарегистрироваться, **Then** система возвращает ошибку "пользователь уже существует"
3. **Given** пользователь вводит слабый пароль, **When** он пытается зарегистрироваться, **Then** система возвращает ошибку с требованиями к паролю

---

### User Story 2 - Вход в систему (Priority: P1)

Зарегистрированный пользователь хочет войти в систему для работы со своими задачами.

**Why this priority**: Основная функция доступа к системе — без входа пользователь не может работать со своими данными.

**Independent Test**: Пользователь с существующим аккаунтом может войти с помощью email и пароля.

**Acceptance Scenarios**:

1. **Given** пользователь имеет аккаунт, **When** он вводит правильные email и пароль, **Then** система предоставляет токен доступа
2. **Given** пользователь вводит неправильный пароль, **When** он пытается войти, **Then** система возвращает ошибку "неверные учётные данные"
3. **Given** пользователь вводит несуществующий email, **When** он пытается войти, **Then** система возвращает ошибку "пользователь не найден"

---

### User Story 3 - Выход из системы (Priority: P2)

Пользователь хочет безопасно выйти из системы для защиты своих данных.

**Why this priority**: Безопасность данных пользователя требует возможности завершения сессии.

**Independent Test**: Пользователь может завершить текущую сессию и токен доступа становится недействительным.

**Acceptance Scenarios**:

1. **Given** пользователь авторизован, **When** он выполняет выход, **Then** токен доступа аннулируется и доступ к защищённым ресурсам блокируется
2. **Given** пользователь уже вышел, **When** он пытается использовать старый токен, **Then** система возвращает ошибку "токен недействителен"

---

### Edge Cases

- Что происходит при множественных неудачных попытках входа (защита от brute-force)?
- Как система обрабатывает запросы с невалидными данными (XSS, SQL injection)?
- Что происходит при отправке запроса без обязательных полей?
- Что происходит при истечении срока действия токена доступа?

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система ДОЛЖНА позволять пользователю зарегистрироваться с уникальным email и паролем
- **FR-002**: Система ДОЛЖНА требовать подтверждение пароля при регистрации
- **FR-003**: Система ДОЛЖНА проверять сложность пароля (минимум 8 символов, буквы и цифры)
- **FR-004**: Система ДОЛЖНА позволять авторизованному пользователю войти с email и паролем
- **FR-005**: Система ДОЛЖНА выдавать токен доступа после успешной авторизации
- **FR-006**: Система ДОЛЖНА позволять пользователю выйти из системы с аннулированием токена
- **FR-007**: Система ДОЛЖНА блокировать аккаунт после 5 неудачных попыток входа на 15 минут
- **FR-008**: Система ДОЛЖНА возвращать понятные сообщения об ошибках без раскрытия чувствительной информации

### Key Entities

- **Пользователь**: Уникальный идентификатор, email, хэш пароля, имя, дата создания, статус аккаунта
- **Токен доступа**: Уникальный идентификатор, привязка к пользователю, время создания, время истечения, статус (активен/аннулирован)

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Пользователь может зарегистрироваться и войти в систему за ≤1 минуты
- **SC-002**: 99.9% запросов авторизации обрабатываются за ≤500ms
- **SC-003**: 95% пользователей успешно завершают регистрацию с первой попытки
- **SC-004**: Система блокирует 100% попыток подбора пароля (brute-force) после 5 неудачных попыток

## Assumptions

- Токены доступа имеют срок действия 7 дней (JWT с expiration)
- Пароли хранятся в хэшированном виде (bcrypt или аналог)
- Поддерживаемые платформы: веб-браузеры, мобильные приложения
- Аутентификация stateless (JWT) для масштабируемости API
